# «30 дней»: архитектура

Документ этапа 1: стек, модули, данные, фоновые задачи, безопасность. Карта экранов лежит в [`SCREENS.md`](./SCREENS.md), ограничения Telegram и Prodamus в [`LIMITATIONS.md`](./LIMITATIONS.md), вопросы владельцу в [`QUESTIONS.md`](./QUESTIONS.md), план и статус этапов в [`PLAN.md`](./PLAN.md).

## 1. Аудит репозитория

В репозитории уже есть два независимых проекта: `backend/` + `frontend/` («100 дней спорта», Express + SQLite) и `hush/` (Express + Postgres + Vite, деплой на Railway). Ни один из них не подходит как основа: у «30 дней» другая модель подписок, рейтинга и данных. Поэтому «30 дней» живёт в отдельной папке `thirty/`, а старые проекты остаются нетронутыми. Из `hush/` взяты проверенные приёмы: проверка `initData`, webhook бота с секретом, один сервис на Railway.

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Монорепозиторий | npm workspaces, TypeScript | без лишних инструментов, совместим с Railway |
| Доменная логика | `packages/domain`: чистые функции, тесты на Vitest | календарь, расписание задач, рейтинг, биллинг и бадди проверяются без БД |
| API, бот, планировщик | `apps/server`: Fastify + Prisma + PostgreSQL | транзакции, уникальные индексы и FK защищают от гонок и двойных списаний |
| Mini App | `apps/miniapp`: React + Vite | Mini App — это SPA внутри Telegram, SSR из Next.js тут не нужен |
| Админка | `apps/admin`: отдельное React + Vite приложение | отдельный бандл и отдельная авторизация (логин, пароль, TOTP 2FA) |
| Очереди и расписание | таблица `Job` в Postgres + планировщик с `pg_advisory_lock` | в ТЗ предложены Redis/BullMQ; заменил, чтобы не держать лишний сервис. Все задачи идемпотентны (уникальные ключи) и переживают рестарт. Если понадобится масштаб, адаптер можно перевести на BullMQ |
| Медиа | `StorageAdapter`: S3-совместимое хранилище, локальный диск в dev | доступ к файлам только через подписанные ссылки |
| Платежи | `PaymentProvider`: `ProdamusProvider` и `MockProvider` (sandbox) | в тестах настоящих списаний нет |
| Деплой | Docker и Railway, один сервис отдаёт API, Mini App (`/`) и админку (`/admin/`) | админку можно вынести на отдельный домен через `ADMIN_ORIGIN` |

## 4. Данные (кратко; полная схема в `apps/server/prisma/schema.prisma`)

- **User** (PK — Telegram id) → **Consent**[] (вид, версия, выдано, отозвано).
- **Tariff** (m1/m3/m6: месяцы, лимит целей, акционная и обычная цена, цена продления, id подписки Prodamus) → **PriceOffer** (персональный 3-часовой таймер, хранится на сервере, создаётся один раз).
- **Subscription** (у пользователя максимум одна живая подписка, частичный уникальный индекс) → **Payment**[] (идемпотентный ключ, уникальный id у провайдера) → **PaymentEvent** (журнал webhook, уникальный хэш тела) → **BillingSchedule** (даты будущих списаний).
- **Flow** (поток = календарный месяц, `startsOn` уникален) → **FlowMembership** (уникальная пара пользователь + поток: оплаченный поток нельзя получить дважды, пересечение периодов невозможно).
- **Goal** → **Task** → **TaskOccurrence** (окно `windowStart..windowEnd` генерируется заранее при фиксации, знаменатель задним числом не меняется).
- **DailyReport** (уникален по членству и дате) → **ReportItem** (отметка по occurrence) → **ReportEvidence** → **MediaFile**. Вокруг отчёта: **ReportComment**, **ReportReaction**, **Complaint**, **ReportAppeal**.
- **BeforeAfter** («ДО» и «ПОСЛЕ» по членству), **GoalFinalAnswer** (итоговая анкета).
- **LeaderboardEntry** (снапшот по потоку), **PrizeCandidate** и **PrizeReview** (журнал решений).
- **BuddyInvite**, **BuddyPair**, **BuddyAssignment** (уникален по потоку и пользователю: не больше одного бадди), **BuddyReplacement**.
- **TelegramChat** (поток или тематический), **ChatMembership**.
- **Expert**, **Meeting**, **Attendance**.
- **Review**, **ShareCard**, **ReferralLink**, **ReferralVisit**.
- **AnalyticsEvent** (уникальный `eventId`), **Experiment**, **ExperimentAssignment**.
- **BotMessageTemplate**, **BotMessageLog** (уникальный `dedupeKey`, клики и конверсии).
- **AdminUser**, **AuditLog**, **Setting** (key-value: часовой пояс, формула фонда, ценность S05, фичефлаги, тексты правил), **Upsell**, **Job**.

## 5. Ключевые правила как код

| Правило | Где | Тест |
|---|---|---|
| Поток = календарный месяц, обязательны все дни (28–31) | `domain/calendar.ts` | февраль, високосный год, 30/31, часовые пояса |
| Покупка до старта → ближайший поток; N месяцев → N потоков подряд | `domain/billing.ts` | 21.10 на 3 мес → ноябрь–январь, списание 28.01 |
| Следующее списание = 28-е число последнего оплаченного месяца | `domain/billing.ts` | нет списаний 28.11 и 28.12 |
| completion_ratio = выполненные обязательные / запланированные обязательные (все цели) | `domain/rating.ts` | 1 и 3 цели с одинаковым % имеют одинаковый вес |
| Идеальный результат: 100%, ни одного пропущенного отчёта, все цели подтверждены | `domain/rating.ts` | пропуск отчёта, неполная итоговая анкета |
| Тай-брейк: % → полностью закрытые дни → самая длинная серия → время подачи итоговой анкеты | `domain/rating.ts` | без бонусов за число целей или фото |
| Лимит целей 1 / 3 / без лимита | `domain/tariffs.ts` | тест на 4 цели в тарифе на 6 месяцев |
| Цена по таймеру считается сервером | `domain/pricing.ts` | истечение, повторное открытие |
| Подбор бадди: сначала пары по приглашению, потом общие интересы, потом совместимость, потом случайно | `domain/buddy.ts` | идемпотентность, нечётное число участников |

## 6. Фоновые задачи (`jobs/`)

Тик раз в минуту под `pg_advisory_lock`, повторный запуск ничего не дублирует:

- дожимные цепочки бота (сегменты из событий воронки, `dedupeKey` на пользователя, шаблон и окно);
- напоминания за 1 час и за 15 минут до конца таймера (только если предложение ещё действует и покупки нет);
- напоминание об отчёте до дедлайна и сообщение после пропуска;
- закрытие дня: occurrence → missed, пересчёт рейтинга;
- 7/14/21/28 день: генерация share-карточек и сообщение;
- старт потока: автоподбор бадди (за 24 ч до старта и повторно в 00:00), смена статуса, ссылки в чаты;
- финал: снапшот рейтинга, PrizeCandidate со статусом `awaiting_review`, просьба оставить отзыв;
- биллинг: синхронизация даты следующего списания с Prodamus, сверка `past_due`, отзыв доступа к чатам после окончания оплаченного срока.

## 7. Безопасность

- Mini App: каждый запрос несёт `Authorization: tma <initData>`, сервер проверяет HMAC и `auth_date`. `user_id` от клиента не принимается.
- Webhook Prodamus: проверка `Sign` (HMAC-SHA256 от отсортированного JSON), повторы отсекаются уникальным хэшем, доступ выдаётся только после подписанного webhook.
- Webhook Telegram: заголовок `X-Telegram-Bot-Api-Secret-Token`.
- Админка: scrypt-хэш пароля, TOTP 2FA (обязательна для owner/admin), JWT в httpOnly SameSite=Strict cookie, CSRF-токен в заголовке, RBAC по ролям, аудит каждого изменения.
- Rate limiting (`@fastify/rate-limit`), лимиты размера тела, валидация zod, Prisma (параметризованные запросы), CSP и экранирование в React.
- Медиа: приватные ключи, выдача через короткоживущие подписанные URL. Чувствительные фото («ДО»/«ПОСЛЕ») видны только автору, админу и проверке призов, публично только при отдельном согласии.
- Персональные данные: минимум полей, город необязателен, удаление аккаунта по запросу (анонимизация отчётов с сохранением статистики), сроки хранения в `Setting`.
