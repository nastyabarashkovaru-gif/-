# Архитектура и данные

## Время и календарь
- В БД — `timestamptz` (UTC) и `date` для локальных календарных дней. Таймзона пользователя — IANA (`users.timezone`), передаётся клиентом при входе, меняется не чаще раза в 6 часов.
- Сутки/недели считаются в таймзоне пользователя через Luxon (DST-безопасно). Неделя — понедельник–воскресенье.
- Дедлайн одноразовой задачи — точный timestamp. Выполнение допустимо при `now <= deadline`; гонка с истечением разрешается блокировкой строки задачи.
- Клиентскому времени сервер не доверяет.

Все балансы — `integer`. Подробная схема: `server/migrations/001_init.sql`.

## Инварианты (гарантируются БД и транзакциями)
- Баланс дерева `>= 0` (CHECK); штраф урезается до доступного остатка, долг не переносится (`requested_amount` хранит исходный размер).
- Одно вознаграждаемое выполнение задачи в локальный день (UNIQUE). Двойной тап → второй запрос возвращает `already: true`.
- Ровно один полив на уровень (UNIQUE `tree_id, from_level`) + ключ идемпотентности клиента + `expectedLevel`.
- Один штраф за период (`pen:<task>:<period>` в UNIQUE `idempotency_key`).
- Капли от задачи идут только дереву её сферы; переводов между деревьями нет.
- Уровень дерева и сада никогда не уменьшается. Уровень сада = функция `sum(total_spent_drops)` (`5·n·(n−1)` капель для уровня n).
- Клиент не может изменить баланс: эндпоинтов для этого нет, все изменения — через `applyDrops()` на сервере.

## Планировщик
`server/src/worker.ts`: каждые 60 с — закрытие периодов задач (`processDueTasks`) и подписки; каждые 10 мин — напоминания.
- У задачи есть `next_process_at` (начало следующего локального дня/недели или дедлайн) и курсор `processed_through`.
- Обработка идемпотентна и догоняет пропущенное: после простоя каждый прошедший день/неделя закрывается ровно один раз.
- Период создания задачи — льготный (без штрафа).
- Смена таймзоны не даёт повторно получить награду/штраф за уже закрытый день (`period_closed`).
- При нескольких репликах задание выполняет одна (`pg_try_advisory_lock`).

## Вредные привычки
- Только в сфере «Здоровье». Ежедневный ответ «Да/Нет», одна запись на день, исправление в тот же день пересчитывает нетто-изменение (`applied_amount`), без повторных наград.
- «Нет» → капли задачи (и +1 к счётчику выполнений для подарков/челленджей), «Да» → 0 (хардкор: −1). День без ответа штрафуется только при хардкоре и явном согласии.
- Визуальное состояние дерева здоровья — ровно `normal | withered` (`healthTreeState` в shared): после последнего «Да» нужно 3 последовательных дня с «Нет»; день без ответа прерывает серию. Уровень и капли не меняются.

## Восстановление после ошибок
- Неуспешные запросы клиента безопасно повторять (идемпотентность).
- Вебхук Telegram: ошибка → 500 → Telegram повторит; повтор с тем же `charge_id` игнорируется.
- Если вебхук об оплате потерян — пользователь не получит доступ; поддержка видит платёж в Telegram и может проверить его в админке. (См. SETUP: мониторинг ошибок.)
- Миграции применяются при старте под advisory lock, транзакционно.
- Резервные копии: включите Backups у сервиса Postgres в Railway.
